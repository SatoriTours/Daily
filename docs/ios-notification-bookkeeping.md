# iOS 27 通知自动记账实施方案

当前交付仅实现 Android。本文记录以后增加 iOS 27 记账功能的实现边界、接口和验证要求，不表示 iOS App 或通知接入已实现。

## 已核实的系统能力

苹果在 iOS 27 快捷指令中新增通知自动化。用户可选择来源 App，并按通知的标题、副标题或正文筛选触发条件。来源：[苹果 iOS 27 快捷指令更新说明](https://support.apple.com/en-us/149045)、[通知触发条件](https://support.apple.com/en-mk/guide/shortcuts/apd932ff833f/ios)。

App 可通过 [App Intents](https://developer.apple.com/documentation/appintents) 提供快捷指令动作。拟采用“选定应用的通知 → 用户配置的快捷指令 → 本 App 的记账动作”路线，不依赖 App 在后台直接枚举其他应用的通知。

**尚未验证**：通知触发的输入变量具体有哪些字段，是否能完整传递正文、来源、时间与标识；锁屏、隐藏通知预览、专注模式和后台执行时的行为；微信、支付宝及目标银行的实际通知模板。官方的触发和筛选说明不能作为这些字段一定可用的证据。第一步必须验证这些条件，再确定自动化模板，不能先承诺完整覆盖。

## 首版范围

- 最低系统版本 iOS 27，不兼容旧版本；不使用越狱、私有 API 或辅助设备转发。
- 记账默认关闭，用户明确开启、选择来源并配置自动化后才接收数据。
- 覆盖通知中能确认的交易。金额、类型不明或疑似重复的放入待确认列表，不猜测隐去的信息，不补回历史通知。
- 提供账目列表、待确认、编辑、忽略、删除、来源原文及按月统计。
- 首版本地规则解析，不接入云端 AI，不上传金融通知，不在日志中输出正文、金额、账号或交易单号。
- 各币种分别统计；转账和还款不计为消费，退款单独统计。时间采用通知接收时间，并明确显示，不冒充银行交易发生时间。

## 复用当前代码

| 当前组件 | iOS 使用方式 |
|---|---|
| `bookkeeping/.../LedgerModels.kt` | 复用状态、账目、收支类型及统计模型 |
| `bookkeeping/.../TransactionParser.kt` | 复用候选筛选、金额／币种／商户／尾号／交易号识别 |
| `bookkeeping/.../LedgerEngine.kt` | 复用入账、信息补全、去重、人工确认和删除身份记录 |
| `bookkeeping/.../LedgerMoney.kt` | 复用整数金额校验、币种精度和展示格式 |
| `shared/.../BookkeepingRepository.kt` | Android SQLDelight 实现；不直接编译进 iOS |

目前 `bookkeeping` 为独立 KMP 模块，仅启用 Android target。整个 `shared` 仍包含 Android 平台实现，不能直接当作可构建的 iOS framework。以后只给 `bookkeeping` 添加 `iosArm64()`、`iosSimulatorArm64()` 和名为 `BookkeepingCore` 的 framework；先验证 Kotlin／Native 与实际 Xcode、iOS 27 SDK 的兼容性，必要时再升级相关构建版本。

仓库目前没有 iOS 工程。新增 `iosApp/` 原生 SwiftUI 宿主、Xcode project 和 App Intents 文件，使用本地 Gradle framework 集成；不额外复制 Kotlin 解析器为 Swift 实现。

## 接入与存储

1. 用一台 iOS 27 iPhone 配置银行／支付应用通知触发，接收真实交易通知，查看可用输入变量。记录支付、收款、退款、重复更新和隐藏内容等匿名化样本，并检查锁屏运行。
2. 若正文可传递，新增“从交易通知记账”App Intent。输入为正文、来源名称／固定来源配置，以及系统实际提供的可选标题、接收时间和事件标识。根据实测字段提供模板，不把没有的输入写成必填。
3. 将来源映射到用户选择的配置。来源字符串本身不是系统认证信息；用户手工运行快捷指令时的输入也不能视为银行证明。微信／支付宝聊天应使用与 Android 相当的支付标题筛选，标题无法获取时先进入待确认，不能放宽为所有聊天都自动入账。
4. 把可用字段交给共享引擎。不要只凭金额和时间自动合并。可靠事件标识优先用于幂等；没有标识时由自动化传入接收时间与来源生成事件键。不能用每次执行重新生成的 UUID 宣称具备重复通知幂等能力，也不能仅对正文哈希而永久吞掉未来同金额交易。
5. Swift 通过一个新增的字符串桥接类调用 Kotlin。建议方法为 `ingest(stateJson, source, eventKey, text, receivedAt)`、`edit(stateJson, id, amount, currency, kind, merchant)`、`dismiss(stateJson, id, status)` 和 `totals(stateJson, start, end)`。桥接返回包含成功标志、结果及固定错误码的 JSON；捕获 Kotlin 异常，避免未声明异常跨 Objective-C 边界导致进程终止。错误不能包含输入原文。
6. 使用 Swift `actor` 统一管理账本读取和修改，调用共享引擎后先完成持久化，再向 App Intent 返回成功。账本版本从 `LedgerState.version = 1` 开始；损坏或未知版本不能降级为空账本并覆盖原文件。
7. Swift 原生存储可使用 CryptoKit AES-GCM 加密整个账本 JSON，密钥放入 Keychain，密文原子写入 Application Support。锁屏自动化如需访问密钥，评估 `AfterFirstUnlockThisDeviceOnly`：重启后首次解锁前必须明确失败，不能用明文后备文件。文件数据保护也应与此一致。
8. 同一宿主进程的界面和 App Intent 共用该 actor。若实际增加独立扩展进程，必须改用具备跨进程事务能力的存储，不能假设 actor 能协调多个进程。UI 每次回到前台刷新账本。

Keychain 密钥不能保证随普通文件备份迁移到新设备。首版应将密文文件排除于自动备份，或实现明确的密码加密导出／导入；不能宣称复制密文文件即可恢复。删除／忽略保留加密的最小身份记录用于防止重复入账，清除原文和商户信息；列表和统计均排除这些记录。

## 界面和配置引导

原生页面展示账本、按币种月度收入／支出／退款、跨月待确认项及来源开关。共享引擎负责金额和账目状态规则；SwiftUI 负责显示、编辑及自动化设置引导。

引导依次说明开启记账、选择来源、添加快捷指令自动化、选择 App、设置交易关键词／支付标题、连接记账动作及传递实际可用变量。执行权限和锁屏选项以实际系统界面为准。不把“允许发送通知”当作“允许读取其他 App 通知”。App 不能在用户不知情时为其建立全来源监听。

如果实测通知触发只能提供事件而无法提供交易正文，停止该接入路线的自动入账实现。保留截图／分享交易文本生成待确认账目的备选入口；Wallet 碰触支付可独立作为补充来源，但不能用它承诺覆盖微信、支付宝或银行卡全部交易。

## 实施顺序和验收

1. 验证真实 iOS 27 通知输入、后台与锁屏执行；确定哪些来源能完整提供正文，哪些只能生成待确认项。
2. 添加 KMP iOS targets 和异常安全的 JSON 桥接；运行现有 `BookkeepingTest`，补充桥接的损坏数据、未知版本及错误输出测试。
3. 创建原生宿主、加密 actor 存储及 App Intent；测试并发重复调用、加密失败、磁盘写入失败和重新启动后数据保留。失败时保留原账本。
4. 添加账本 UI、来源开关、月度统计和自动化引导；验证确认、编辑、删除、重复通知与币种精度。
5. 使用 Xcode 编译、单元测试后，在明确授权设备测试或准备发布时执行 iPhone UI 和通知自动化验收。验证银行交易、微信／支付宝支付标题、普通聊天、验证码、余额、营销、退款、转账、还款和相同金额的不同交易。

验收必须证明：可靠重复事件只生成一笔账目；疑似重复保留待确认；用户编辑或删除后的通知更新不会自动覆盖账目；待确认／转账／还款不计入消费；数据与密钥错误不会清空原账本；通知被隐藏或漏收时不会编造交易。
