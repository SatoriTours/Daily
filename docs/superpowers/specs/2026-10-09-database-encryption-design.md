# 数据库整库加密与跨设备备份恢复

日期：2026-10-09

状态：设计待用户审阅；尚未实施。

源码核查基线：`bc2b6a56`。实现时保留工作区内其他任务的修改。

## 1. 已确认的目标

- 数据库文件离开应用后不能由普通 SQLite 工具直接读取；数据库内普通字段和凭据不再重复加密。
- 数据库密码由应用随机生成并自动使用，由 Android Keystore 密钥保护，不要求用户每次启动输入密码。
- 用户继续使用独立的备份密码。备份可在卸载重装或其他设备上恢复，不依赖原设备 Keystore。
- 跨设备恢复沿用备份里的数据库密码，只重新用目标设备 Keystore 保护该密码，不进行一次整库重加密。
- SQLCipher 支持日后更换数据库密码；这与更换保护密码的 Keystore 密钥不同，前者需要重写数据库。此次不新增手动轮换密码的设置入口。
- 旧数据库、旧字段密文和已有备份必须兼容；失败不能以清空字段、重建空数据库或部分覆盖代替恢复。

## 2. 当前状态与范围

`DatabaseDriverFactory.android.kt` 使用普通 `AndroidSqliteDriver`，没有整库密码。AI、MCP、远程新闻、收藏源、Skill、微信读书、语音配置、短信、账目、手机消息等字段使用 `SecretCipher` 单独加密；启动时还会扫描并加密字段。

现有备份是密码加密的 ZIP，数据库快照中先解开字段密文；恢复时再次按目标设备加密。已有清单校验、备份验证和启动前文件替换/回滚事务，优先扩展而不重写。

本次范围：数据库驱动和密钥生命周期、一次性旧库转换、数据库字段读写、备份/验证/恢复、相关诊断读取与测试。

边界：

- `life_archive/archive.json.enc` 是数据库之外的独立资料文件，仍须加密；保留现有资料备份/恢复，不迁入数据库，也不删除它依赖的旧 Keystore 密钥。
- 图片、录音等附件不因数据库加密而自动加密。本次不改变附件落盘方式，备份中的附件仍由备份密码保护。
- 不提供应用锁、生物识别入口或每次启动输入密码；这些不是数据库文件加密。
- 不重命名 `encrypted_source` / `encrypted_payload` 等历史列，避免无收益的 Schema 迁移；这些列在新模式下保存普通序列化数据。

## 3. 方案选择

采用 **SQLCipher 加密数据库 + Keystore 包装随机数据库密钥 + 用户密码保护便携备份**。

不采用以下方案：

1. 继续字段级加密：不能覆盖日记、文章、索引等全库数据，也会继续增加备份与迁移分支。
2. 恢复时为目标设备重新生成数据库密码并整库转换：可行，但会增加恢复的读写和耗时；用户已明确选择沿用备份密钥。
3. 把 Keystore 密钥或设备包装后的密码直接复制进备份：Keystore 密钥不可跨设备移植，无法可靠恢复。

## 4. 驱动与密钥所有权

- 保留 SQLDelight Repository/查询层；Android 驱动通过官方维护的 `net.zetetic:sqlcipher-android` 与 `SupportOpenHelperFactory` 接入，不使用已弃用的 `android-database-sqlcipher`。
- 依赖锁定到经过编译与打包检查、支持项目 minSdk 26 和 Android 16 KB 内存页的官方稳定版本；沿用当前 AndroidX SQLite 兼容接口，不顺带升级无关依赖。
- 生成 32 字节高熵随机数据库密钥。SQLCipher 使用明确的 raw-key 表达，避免将随机密钥当作用户口令重复运行昂贵的口令派生。备份记录密钥编码和 SQLCipher 格式配置，恢复时严格匹配。
- 新增单一密钥管理组件：数据库密钥仅在内存、Keystore 包装后的私有 `database_key.sec`、或受用户密码保护的备份内容内存在。
- Android Keystore 保存不可导出的 AES-256 包装密钥；私有文件保存带版本的 AES-GCM 密文和随机 IV。数据库密码本身不以明文写入 Setting、日志、诊断、SharedPreferences、迁移日志或恢复标记。
- 文件写入采用临时文件、同步和原子替换。读取已有密钥失败必须报错，不能自动生成新密码覆盖旧密码。只有确认没有既有数据库和待提交事务的新安装才能初始化。
- 工厂显式区分活动库、带指定密钥的备份/待恢复库、仅兼容旧格式的明文库、测试内存库。禁止“打开失败就用无密码再试”或用活动库密钥猜测备份密钥。
- 数据库格式探测只用于识别既有明文 SQLite；缺少明文头不等于已验证加密，必须以正确密钥读取并执行完整性校验。不得配置明文数据库头。
- 初始化/迁移/恢复共享进程启动前的文件锁；普通数据库读写在准备完成后才启动。密码与数据库文件由一个事务所有者切换，后台工作不能独立创建另一份密码。

## 5. 旧库与旧字段迁移

顺序：处理未完成的文件事务 → 确定数据库格式和密钥 → 必要时转换旧库 → 初始化业务 DI → 常规 Schema 迁移 → 启动后台工作。

旧明文数据库转换：

1. 在业务连接和 Worker 开启前锁定初始化流程；源数据库不进行字段改写。
2. 用 SQLCipher 的显式加密导出创建私有加密候选库，保留表、索引、触发器、数据及 `PRAGMA user_version`，并保留 Setting 中业务 Schema 版本。源库 WAL 中已提交的数据必须纳入一致快照。
3. 在加密候选库内按旧字段注册表严格解密既有字段。检查真实存在的表/列，兼容旧 Schema；可恢复的旧字段转为普通值，无法解密则中止，不清空、不保留无法使用的密文伪装成功。
4. 校验 SQLite/SQLCipher 完整性、外键、全部应用表行数与内容语义；候选库关闭后重新用候选密钥打开确认。
5. 把候选数据库与包装后的密钥作为同一可恢复事务提交。替换前关闭连接、完成 checkpoint 并正确处置 WAL/SHM/journal，不单独拷贝 WAL 主文件。
6. 提交成功后清理旧明文文件、旧边车和暂存目录。失败/中断保留或还原原库，下一次启动重试或进入恢复路径，不开启明文降级模式。

删除活动库每次启动的字段加密扫描。Repository、SpeechSettingsService、微信读书旧配置迁移等改为读写普通值，移除数据库用途的 Cipher 注入，而不是把全局 Cipher 改成空操作。保留旧 Cipher 供历史兼容和独立资料文件使用。

旧字段兼容转换必须覆盖当前注册表中的所有字段，包括账目、手机消息、短信原文、屏蔽发送者和语音配置。Schema 迁移后可能新落入数据库的历史凭据也不得重新加密。

## 6. 新备份格式

外层仍是用户选择的目录内、由用户备份密码保护的 `.zip.enc`；继续支持流式处理，不把整个备份加载进内存。

内容清单升级为版本 2，明确记录数据库为 SQLCipher、兼容格式和密钥描述文件。ZIP 包含：

- 一致的加密数据库快照；
- `database_key.json`：版本、密钥编码、32 字节数据库密钥和必要 SQLCipher 格式参数；
- 现有用户附件、便携生活资料快照和清单。

上述密钥描述文件只位于密码加密备份的内部及应用私有短期暂存区；不能作为未加密旁路文件导出，也不能复制 `database_key.sec` 充当便携密钥。清单登记并校验它，通用附件扫描必须排除所有密钥文件、密钥目录与事务目录。

快照明确用密钥保护导出目标，不能直接沿用普通 SQLite 的 `VACUUM INTO` 并假设输出一定加密。新快照验证包括正确密钥可读、无密码/错误密钥不可读、字段值已不再额外加密。显式保留 `user_version`。

数据库快照可以使用同一数据库密钥及独立的 SQLCipher 盐；恢复不重新导出全库。快照生成本身仍需复制数据库数据，不能承诺备份与恢复零 I/O。

现有外层使用 DSB2 流式加密与固定 10,000 次 PBKDF2。由于新备份包含整库密钥，新写入改用 DSB3 外层头：记录 PBKDF2-HMAC-SHA256 600,000 次、盐与 IV，并把头与密文一起认证；沿用现有 AES-CTR + 独立 HMAC 密钥的流式结构。解析限制 KDF 标识、参数范围及长度，认证通过前不使用解包内容。保留 DSB2 和历史 AES-GCM 的读取，不能在旧格式魔数下改变派生参数。该派生每次备份/恢复仅进行一次，不对每页或每字段重复执行。

用户备份密码仍通过现有 Keystore 包装保存，不与数据库密钥混用。改变备份密码影响新生成的备份；已有备份仍使用各自原密码。

## 7. 恢复与验证

新格式恢复：

1. 先用输入的备份密码认证并解密外层，再解包并检查清单、路径、大小、摘要和版本。
2. 严格读取便携数据库密钥，用该密钥打开恢复副本；执行 SQLCipher 与 SQLite 完整性校验、全表可读验证。
3. 在恢复副本内完成必要 Schema 升级、附件路径重定位和目标设备设置修正；仅修改必要页，不执行整库换密钥。
4. 将备份中的数据库密钥用目标设备自己的 Keystore 包装为新的 `database_key.sec`。恢复过程中不得提前更新活动密钥文件。
5. 暂存数据库、包装密钥、附件、现有生活资料及备份密码。恢复事务扩展 `database_key.sec` 目标，与数据库一起提交或一起回滚，绝不能出现“新库 + 旧密码”或“旧库 + 新密码”。
6. 复用现有重启后、业务初始化前应用恢复的模式；处理中断、磁盘不足、包装失败和回滚重试。

备份验证走相同解密/格式分支，但始终只在验证副本上执行；不修改活动数据库、数据库密钥、资料或备份密码，不发布待恢复任务。

旧格式兼容：

- DSB2/历史外层和清单版本 1、无清单旧备份仍可读取。
- 旧备份的明文数据库在私有暂存区转换为加密候选库，生成独立随机密钥，随后走相同事务；旧格式恢复会有一次整库转换，快速恢复保证仅针对新格式。
- 旧字段仍有 `enc:v1:` 密文时严格尝试已有兼容密钥；无法解开则取消恢复并解释原因。原设备密钥已经丢失的旧字段没有通用解密方法，不谎称跨设备可恢复。
- 未来格式、超出支持范围的 Schema、缺失或不匹配的密钥一律拒绝，不自动创建数据库。
- 旧备份缺少生活资料时，继续保留本机资料的现有行为。

## 8. 密钥丢失、诊断与安全边界

密钥缺失/失效/损坏时停止业务数据库初始化，不调度后台工作，不删除数据库。诊断独立进程仍可启动，提示可从用户密码保护的备份恢复。

现有诊断更新配置直接用系统 SQLite 读取数据库，应改为轻量、只读的 SQLCipher 读取，使用既有包装密钥，不依赖业务 DI，不生成密钥、不迁移、不改库。SQLCipher 原生库或 Keystore 不可用时继续沿用安装包默认更新配置并注明降级，不能连带破坏诊断入口。历史明文库只允许该只读兼容路径，不作为业务运行降级。

不记录含密钥 SQL 或原始异常消息；对数据库打开/迁移/恢复失败输出安全类别。内存中密钥限制生命周期并尽可能清零，不能承诺 JVM 完全无内存副本。

成功后清理暂存明文 ZIP、便携密钥、旧库和恢复回滚副本；中断后的暂存由启动前事务状态决定恢复或清理。闪存删除不保证安全擦除；root/被控制进程、已经解锁的应用内读取、运行时内存与数据库外附件不是本次加密能完全防御的对象。拥有正确备份密码的人也能取得相应数据库密钥，这是便携恢复的必要能力。

同一数据库密钥在恢复设备间沿用，因此若密钥实际泄漏，应另行轮换；仅重新包装不能撤销旧密钥或旧备份。

## 9. 验收与验证

代码级测试：

- 普通 SQLite/无密码/错误密钥不能读取新库，正确密钥可读取；数据库及加密边车不包含测试明文标记。
- 旧库转换保留所有应用表、字段语义、索引、版本和已提交 WAL 数据；字段严格解密失败、磁盘不足、事务各阶段中断均不丢失原数据。
- Repository 新写入不额外加密，所有历史注册字段成功迁移；资料文件仍加密可用。
- 新备份、错密码、篡改头/密文/清单/密钥、截断、不支持参数、旧 DSB2/历史外层、旧清单及旧字段兼容。
- 模拟两个不同设备包装密钥：备份设备和恢复设备不能互解包装文件，但恢复后的数据库使用原数据库密钥正常工作。新格式恢复断言未调用整库导出/换密钥路径。
- 新密钥文件纳入恢复事务；每个替换阶段失败/中断均同时还原数据库和密码；验证操作不修改活动状态。
- 密钥丢失时不覆盖、不建空库；独立诊断和默认更新回退不回归。

日常先跑受影响聚焦测试，再合并执行必要模块测试、`:app:compileDebugKotlin` 和 `:app:assembleDebug`（本次引入原生依赖，需打包检查）。不启动模拟器、不安装运行 App、不执行 UI 测试。

JVM 的普通 SQLite 驱动/假 Cipher 不能证明 Android SQLCipher 原生链路真实有效。实施时需用可用的主机 SQLCipher 对真实文件进行加密/导出/完整性基础验证，并检查 APK ABI 与原生库 16 KB 对齐；Android Keystore 与 JNI 的设备端端到端验证留待用户明确授权设备测试或发布前执行。缺失主机工具或设备验证时如实记录未验证范围，不把 Mock 测试记作原生链路通过。

不修改 AI 提示词、请求协议或解析；凭据存储改动用本地 Repository/备份往返测试验证，不为此重复消耗真实 AI 调用。

- `shared/.../platform/DatabaseDriverFactory.android.kt`：SQLCipher 工厂与明确的打开模式。

- `shared/.../data/repository/`、`SpeechSettingsService.kt`、`WeReadSkillService.kt`、`DatabaseMigration.kt`、`SharedModule.kt`：移除数据库重复加密。
